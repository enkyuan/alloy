# Kaji v0.3 Plan: Intent-to-Execution Runtime

> **Status:** implementation plan for the v0.3 alpha milestone  
> **Audience:** implementation and review agents working in `enkyuan/alloy`  
> **Authority:** this file is authoritative for this milestone once reviewed and frozen  
> **Goal:** shift Kaji from "an embeddable agent SDK" toward the framework-neutral execution layer between agent intent and real product actions, without rewriting the existing runtime kernel

---

## 0. One-sentence thesis

**Kaji is the execution layer between an agent deciding to do something and a product safely carrying that action out.**

Kaji should let a product team expose its native capabilities to any agent/model while Kaji handles the execution envelope: identity, policy, approval, durable task state, idempotency, cancellation, failure semantics, artifacts, and replay.

The model or agent framework decides **what should happen**.  
The product owns **how its domain works**.  
Kaji owns **how agent intent becomes a safe, reliable execution**.

---

## 1. Rules for implementation agents

1. **Do not redesign the architecture while implementing a slice.**
   - If implementation reveals a contradiction, stop that slice and record the contradiction, the smallest affected public contract, two possible fixes, and the existing Kaji invariant that is violated.
   - Do not silently introduce a new abstraction.

2. **Keep the pivot additive.**
   - Do not rename or remove `ToolSpec`, `ToolRegistry`, `ToolPlanner`, `AgentBuilder`, `AgentRuntime`, the event journal, approval, or idempotency contracts.
   - New product-facing abstractions adapt to the existing execution kernel.

3. **Do not broaden the milestone.**
   - No MCP.
   - No A2A.
   - No graph/workflow DSL.
   - No multi-agent framework.
   - No hosted service.
   - No new provider promotion.
   - No Ryo-specific code in Kaji core.
   - No package/brand rename.

4. **One slice, one reviewable commit.**
   - Every slice includes tests.
   - A slice is complete only when its acceptance tests and relevant legacy suite pass.

5. **Python and TypeScript semantics must match.**
   - Naming may follow language conventions.
   - Behavior, states, durable schemas, errors, event ordering, and limits must match.

6. **Preserve fail-closed semantics.**
   - Unknown risk stays invalid.
   - Tool-capable execution still requires principal identity.
   - Unknown external side effects are never silently retried.
   - Raw journal data remains privileged.

7. **Do not weaken existing release gates to make v0.3 pass.**

## 2. Current architecture we are extending

The current execution spine is the kernel:

```text
AgentBuilder
    ↓
ToolRegistry
    ↓
ToolPlanner + ToolPolicy + Approval
    ↓
AgentRuntime
    ↓
EventStore / Event journal
    ↓
Provider + Tool execution
```

v0.3 must reuse:

- validated `ToolSpec` schemas and explicit risk
- `ToolPolicy` allow/deny and risk-threshold approval
- principal propagation
- execution context carrying session/turn/call/trace/deadline/cancellation/idempotency
- `not_started` versus `unknown` side-effect outcomes
- `ToolIdempotencyLedger`
- session-local event sequencing
- replay by sequence, not timestamp
- bounded turn cancellation/deadline semantics
- `Integration.register()`
- cross-SDK parity machinery

## 4. Milestone definition

v0.3-alpha is complete when a clean-installed Python and TypeScript package can demonstrate:

1. A developer declares an existing product function as a **Capability**.
2. The Capability executes through the existing Kaji tool kernel.
3. A user starts a durable **Task** with a principal and an intent.
4. The Task exposes state, event history, cancellation, and terminal result.
5. A Capability can produce one or more first-class **ArtifactRef** values.
6. Kaji persists execution through a supported Postgres backend.
7. A process can die and a new process can recover the task without blindly duplicating an external side effect.
8. The same scenario has deterministic Python/TypeScript parity tests.
9. Existing `AgentRuntime.turn()` and integrations still work unchanged.
10. One end-to-end example demonstrates a real mutable product action.

Success criterion:

> A product function can be safely exposed to an agent with very little application code, and Kaji preserves the execution semantics when the operation becomes risky, long-running, interrupted, or stateful.

## 5.1 Capability

A **Capability** is a product operation an agent may request.

Examples:

```text
payments.refund
payments.create_transfer
figma.update_node
repo.create_commit
deployments.deploy
crm.update_account
```

In v0.3 it is a thin abstraction compiled into the existing `ToolSpec` + `ToolRegistry` + handler path.

### Required fields

```text
name
description
input schema
risk
execute
```

Optional fields should reuse existing ToolSpec behavior:

```text
timeout
parallel-safe
metadata
```

Do not create a second copy of timeout/risk/concurrency logic.

### TypeScript target DX

```ts
import { capability } from "@irogane/kaji";
import { z } from "zod";

export const refundPayment = capability({
  name: "payments.refund",
  description: "Refund a settled payment",
  risk: "destructive",

  input: z.object({
    paymentId: z.string(),
    amount: z.number().int().positive(),
  }),

  async execute(input, ctx) {
    return payments.refund({
      paymentId: input.paymentId,
      amount: input.amount,
      idempotencyKey: ctx.idempotencyKey,
      principalId: ctx.principalId,
    });
  },
});
```

### Python target DX

```python
import kaji

@kaji.capability(
    name="payments.refund",
    description="Refund a settled payment",
    risk="destructive",
    input_schema={
        "type": "object",
        "properties": {
            "paymentId": {"type": "string"},
            "amount": {"type": "integer", "minimum": 1},
        },
        "required": ["paymentId", "amount"],
        "additionalProperties": False,
    },
)
async def refund_payment(input, ctx):
    return await payments.refund(
        payment_id=input["paymentId"],
        amount=input["amount"],
        idempotency_key=ctx.idempotency_key,
        principal_id=ctx.principal_id,
    )
```

If an existing typed input/decorator path preserves exact cross-SDK JSON Schema semantics, reuse it. Do not add a new validation system just for Capability.

### Registration

TypeScript:

```ts
const runtime = new AgentBuilder()
  .provider(provider)
  .capability(refundPayment)
  .build();
```

Python:

```python
runtime = (
    kaji.AgentBuilder()
    .provider(provider)
    .capability(refund_payment)
    .build()
)
```

`AgentBuilder.capability(...)` must register through the same scoped registry/planner path as existing integrations.

Existing `.integration(...)`, `tool`, `function_tool`, `ToolSpec`, and direct registry APIs remain valid.

### Invariant

```text
Capability
    ↓ compile/adapt
ToolSpec + handler
    ↓
existing Kaji execution
```

There must not be two execution paths.

## 5.2 CapabilityResult

Ordinary Capability handlers may keep returning durable JSON.

A handler exposing product outputs as first-class artifacts returns a `CapabilityResult`.

```ts
interface CapabilityResult<T = unknown> {
  value?: T;
  artifacts?: readonly ArtifactRef[];
}
```

Python equivalent should be immutable.

Rules:

1. `value` is exposed back to the model/tool loop.
2. `artifacts` are recorded as first-class Kaji events and projected onto the Task.
3. Underlying tool results still obey current durable result rules.
4. Artifact references must not carry arbitrary binary or oversized payloads.
5. Plain JSON remains supported and emits no artifact event.

Example:

```ts
return capabilityResult({
  value: { refunded: true },
  artifacts: [
    artifact({
      id: refund.id,
      type: "ryo/refund",
      uri: `ryo://refunds/${refund.id}`,
    }),
  ],
});
```

## 5.3 ArtifactRef

An **ArtifactRef** points to a product-native output created or changed by an execution.

Examples:

```text
ryo://payments/pay_123
figma://files/abc/nodes/123
git://repo/abc/commit/91afd
deploy://production/releases/381
crm://accounts/acct_91
```

Kaji stores reference + provenance. The host product remains source of truth.

### Contract

```ts
interface ArtifactRef {
  id: string;
  type: string;
  uri: string;
  version?: string;
  mediaType?: string;
  metadata?: Readonly<Record<string, JsonValue>>;
}
```

Python must provide an equivalent immutable value object.

### Validation

Require:

- non-empty `id`
- non-empty namespaced `type`
- URI with a scheme
- optional non-empty `version`
- optional media-type string
- metadata satisfying durable JSON rules
- serialized ArtifactRef inside the existing durable-value limit

Do not:

- download the artifact
- store binary contents
- require HTTP URLs
- assume artifacts are files
- add an artifact database

### Event

Add:

```text
artifact.emitted
```

Payload must correlate the artifact to the Task, turn, capability/tool call, and canonical journal sequence. Reuse existing event-envelope identity fields rather than duplicating them.

### Projection

`TaskSnapshot.artifacts` returns artifacts in journal sequence order.

Artifact IDs are unique within a Task projection. Conflicting duplicates fail projection rather than silently choosing one.

# 6. Task

## 6.1 Definition

A **Task** is one durable unit of agent-directed product work.

Examples:

```text
"refund this customer's damaged order"
"deploy the approved release"
"turn this wireframe into a checkout flow"
"pay these approved invoices"
```

A Task is not a graph engine.

For v0.3, a Task wraps one goal-oriented execution using the existing `AgentRuntime`. It may include provider turns, Capability calls, approvals, recovery, and artifacts.

### Public names

```text
TaskRuntime
TaskHandle
TaskSnapshot
TaskState
```

Do not call it `Workflow`.

---

## 6.2 Task states

Freeze v0.3 to:

```text
created
running
waiting_for_approval
suspended
reconciliation_required
completed
failed
cancelled
```

Semantics:

- `created`: Task identity and creation are durable.
- `running`: execution currently owns the Task.
- `waiting_for_approval`: a canonical Kaji approval request is durably pending.
- `suspended`: execution intentionally stopped at a resumable safe boundary.
- `reconciliation_required`: a side effect cannot be proven completed or not-started.
- `completed`: terminal success.
- `failed`: terminal failure.
- `cancelled`: terminal cancellation.

Terminal:

```text
completed
failed
cancelled
```

`reconciliation_required` is resumable after explicit host reconciliation.

Invalid transitions fail deterministically.

Never infer ordering from timestamps.

---

## 6.3 Task identity versus session identity

Publicly, `task_id` and `session_id` are distinct concepts.

The v0.3 implementation may map one Task to one underlying session to reduce complexity, but:

- do not document equality as a contract
- callers must not depend on equality
- new APIs use `task_id`
- adapter code owns task/session mapping

This leaves room for future multi-task sessions or tasks spanning multiple model sessions.

## 6.4 TaskRuntime API

TypeScript target:

```ts
const tasks = new TaskRuntime({
  runtime,
  backend,
});

const task = await tasks.start({
  principalId: "user_123",
  input: "Refund order #1842",
  metadata: { orderId: "1842" },
});

const snapshot = await task.snapshot();

for await (const event of task.events()) {
  // progress
}

await task.cancel();
```

Python target:

```python
tasks = kaji.TaskRuntime(
    runtime=runtime,
    backend=backend,
)

task = await tasks.start(
    principal_id="user_123",
    input="Refund order #1842",
    metadata={"orderId": "1842"},
)

snapshot = await task.snapshot()

async for event in task.events():
    ...

await task.cancel()
```

Required operations:

```text
TaskRuntime.start(...)
TaskRuntime.get(task_id)

TaskHandle.snapshot()
TaskHandle.events(after_sequence=...)
TaskHandle.cancel()
TaskHandle.resume(...)
TaskHandle.pending_approvals()
TaskHandle.decide_approval(...)
```

Do not add a large convenience surface.

---

## 6.5 Task lifecycle events

Add only the minimum explicit lifecycle events:

```text
task.created
task.suspended
task.resumed
task.completed
task.failed
task.cancelled
artifact.emitted
```

Prefer projection from existing canonical execution events:

- `waiting_for_approval` should derive from existing approval request/decision events.
- `reconciliation_required` derives **only** from journaled `tool.call.failed` events with `outcome: "unknown"`, never from ledger reads.

Principle:

> Task state is a projection over the canonical execution journal wherever possible, not a parallel truth source.

---

## 6.6 Approval resume

Use the existing event-backed approval contract.

`TaskHandle.pending_approvals()` should expose a host-safe projection.

Conceptual shape:

```ts
interface PendingApproval {
  id: string;
  capability: string;
  risk: ToolRisk;
  arguments: JsonValue;
}
```

Internally, opaque `id` may map to the canonical `(turn_id, tool_call_id, tool_name)` identity.

Approval decisions must still produce existing canonical approval events.

Do not create a second approval journal.

# 7. Durable backend

## 7.1 Goal

Keep Kaji core infra-free while giving developers an obvious production path:

```text
prototype:
    InMemoryBackend

production:
    PostgresBackend
```

Do not require Redis in v0.3.

---

## 7.2 Backend composition

Introduce one composition boundary:

```ts
interface RuntimeBackend {
  eventStore: EventStore;
  committer: EventCommitter;
  idempotencyLedger: ToolIdempotencyLedger;
  turnCoordinator: TurnCoordinator;
}
```

The TypeScript `committer` must match `eventStore`; `AgentRuntime` requires that `EventCommitter` append/subscription seam. The Python equivalent uses `event_store`, `journal`, `idempotency_ledger`, and `turn_coordinator`: `AgentRuntime` takes a store plus an optional `EventJournal`, and when a journal is supplied `journal.store is store`.

`PostgresBackend` must implement this committer/journal seam rather than pairing a Postgres store with an in-memory committer or journal.

Built-ins:

```text
InMemoryBackend
PostgresBackend
```

`InMemoryBackend` composes existing in-memory implementations rather than duplicating them.

Existing low-level injection APIs remain available.

---

## 7.3 Package placement

Keep Postgres optional.

TypeScript:

```text
@irogane/kaji/postgres
```

Python:

```text
kaji[postgres]
```

Do not make a Postgres driver mandatory for core Kaji.

## 7.4 Shared SQL contract

Create one canonical schema:

```text
kaji/contracts/postgres/v1/schema.sql
```

Both SDKs implement the same semantics.

### Event table

```sql
kaji_events
-----------
session_id
sequence
event_id
event_json
created_at
```

Constraints:

```text
PRIMARY KEY (session_id, sequence)
UNIQUE (event_id)
```

Sequence allocation must be atomic per session.

### Idempotency table

```sql
kaji_tool_idempotency
---------------------
session_id
tool_call_id
fingerprint
status
result_json
error_json
created_at
updated_at
```

Unique:

```text
(session_id, tool_call_id)
```

Durable states match existing ledger semantics:

```text
running
completed
unknown
```

Retryable failure releases the claim according to current Kaji semantics instead of inventing a false terminal status.

Interop pin: compute `fingerprint` as SHA-256 over canonical JSON for `[tool_name, tool_args]` with `sort_keys=True`, compact separators `(',', ':')`, `ensure_ascii=False`, and `allow_nan=False`, matching `kaji/packages/py/src/runtime/tools/idempotency.py` `_fingerprint`.

The row state machine is `running` → `completed` or `unknown`; a retryable failure releases the `running` claim so it may be claimed again. A matching fingerprint observes its current row; a different fingerprint conflicts. No timeout converts `running` to a safe terminal state.

### Coordination

Prefer the simplest correct Postgres-based cross-process coordinator.

For v0.3-alpha, a Postgres advisory lock held on a dedicated pooled connection for the duration of a turn is acceptable if:

- lock identity is deterministic and identical in Python/TS
- cancellation while waiting releases cleanly
- connection loss fails closed
- process crash releases the server-side lock
- pool capacity bounds active locks
- docs state the scaling tradeoff

Do not build a lease/heartbeat/fencing subsystem unless advisory locking proves incompatible with current semantics.

Correct and simple beats prematurely scalable.

## 7.5 Crash semantics for durable idempotency

Critical invariant:

```text
1. Kaji claims an external-effect call
2. handler performs external mutation
3. process dies before Kaji records completion
4. new process recovers
```

The new process must **not** execute the call again automatically.

A durable ledger row left `running` by a dead process is ambiguous after restart.

It must fail closed into an unknown/reconciliation-required path rather than being reclaimed by timeout.

There is no timeout that proves an external mutation did not happen.

Provide explicit reconciliation:

```text
external system proves completed
    ↓
mark completed with reconciled result
    ↓
resume Task
```

or:

```text
external system proves not started
    ↓
explicitly release/retry
```

TaskRuntime surfaces `reconciliation_required`.

# 9. Integration lifecycle

Existing:

```text
Integration.register(registry)
```

remains supported.

The new Capability design must leave room for later:

```text
async initialize
managed close/dispose
host credential resolution
compatibility metadata
```

Do not accidentally freeze a richer lifecycle through an overly rigid Capability contract.

A Capability must be usable without an Integration. An Integration may register one or many Capabilities.

# 10. Artifact and journal safety

The raw Kaji journal remains privileged.

`Task.events()` is not automatically a safe observability feed.

Document that it may contain:

- prompts
- provider text
- capability/tool arguments
- tool results
- metadata

`TaskSnapshot` should expose only minimum control-plane state:

```text
task id
state
principal id if host-authorized
sequence cursor
timestamps
artifact refs
terminal error code
pending approval projection
```

Do not copy raw provider/tool payloads into TaskSnapshot.

A safe/redacted journal projection helper remains a separate surface unless already available.

## B4: Restart/recovery system test

Create a fixture Capability representing an external mutation using a separate durable fixture table.

Scenario:

```text
process A
  starts Task
  claims Capability
  writes external side effect
  crashes before Kaji records completion

process B
  loads Task
  sees unresolved durable execution
  DOES NOT execute Capability again
  Task becomes reconciliation_required

host reconciliation
  proves external side effect exists
  records reconciled result

process B
  resumes Task
  completes
```

Assertions:

```text
external side-effect row count == 1
Task eventually completed
journal retains evidence
artifact/result matches reconciled object
```

Also prove:

```text
process dies before handler begins
→ retry is allowed
```

These cases must remain distinct.
