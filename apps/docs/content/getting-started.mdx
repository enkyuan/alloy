---
title: Getting Started
description: Install kaji, define a tool, and run an agent turn end-to-end. Python and TypeScript.
---

This page takes you from `install` to a working agent in five steps. By the
end you'll have sent a user message and received a model response, with one
tool wired in.

<Steps>
  <Step>
    ### Install

    <Tabs items={["python", "typescript"]}>
      <Tab value="python">
        ```bash
        pip install "kaji-sdk[openai]"
        ```
      </Tab>
      <Tab value="typescript">
        ```bash
        bun add @kaji/sdk "zod@>=4.3 <5" openai
        ```
      </Tab>
    </Tabs>

    These pull the SDK plus one provider client. TypeScript also requires Zod
    `>=4.3 <5` as a peer dependency. For other providers or optional extras,
    see [install](/docs/install).

  </Step>

  <Step>
    ### Set a provider key

    Pick one provider and export its key. The base SDK uses a mock provider for
    tests until you configure a real one; scaffolds generated with
    `--provider openai` set `KAJI_MODEL_PROVIDER=openai`.

    ```bash
    export OPENAI_API_KEY=sk-...        # or
    export ANTHROPIC_API_KEY=sk-ant-... # or
    export OPENROUTER_API_KEY=...        # Kimi/OpenRouter
    ```

    To choose another provider, set `KAJI_MODEL_PROVIDER=openai`,
    `anthropic`, `gemini`, or `kimi`.

  </Step>

  <Step>
    ### Define a tool

    Tools are a spec (name, description, JSON Schema parameters, and risk)
    plus a handler. The `@function_tool` decorator (Python) /
    `functionTool(...)` helper (TS) derives the parameter schema from type
    hints or Zod. Every enabled tool must declare risk explicitly.

    <Tabs items={["python", "typescript"]}>
      <Tab value="python">
        ```python
        import kaji

        @kaji.function_tool(risk="read")
        async def get_weather(
            context: kaji.ToolExecutionContext,
            city: str,
        ) -> dict:
            """Look up the weather for a city."""
            return {
                "city": city,
                "tempF": 68,
                "principal": context.principal_id,
            }
        ```
      </Tab>
      <Tab value="typescript">
        ```ts
        import { functionTool } from "@kaji/sdk";
        import { z } from "zod";

        const getWeather = functionTool(
          {
            name: "get_weather",
            description: "Look up the weather for a city.",
            parameters: z.object({ city: z.string() }),
            risk: "read",
          },
          async ({ city }, context) => ({
            city,
            tempF: 68,
            principal: context.principalId,
          }),
        );
        ```
      </Tab>
    </Tabs>

  </Step>

  <Step>
    ### Build the runtime

    `AgentBuilder` wires a provider and tools to the runtime's event
    journal/committer, producing a runnable `AgentRuntime`.

    <Tabs items={["python", "typescript"]}>
      <Tab value="python">
        ```python
        from kaji import AgentBuilder, get_provider

        runtime = (
            AgentBuilder()
            .provider(get_provider("openai"))
            .tool(get_weather)
            .system_prompt("You are a helpful assistant.")
            .build()
        )
        ```
      </Tab>
      <Tab value="typescript">
        ```ts
        import { AgentBuilder, deadlineAfter, OpenAIProvider } from "@kaji/sdk";

        const runtime = new AgentBuilder()
          .provider(new OpenAIProvider({ apiKey: process.env.OPENAI_API_KEY! }))
          .tool(getWeather)
          .systemPrompt("You are a helpful assistant.")
          .build();
        ```
      </Tab>
    </Tabs>

    No DB or server is required. The runtime uses a bounded in-memory event
    store and atomic in-memory journal/committer by default.

  </Step>

  <Step>
    ### Run a turn

    `turn()` appends the user message, runs one model/tool loop, and returns
    the final assistant text. The model decides whether to call your tool; the
    runtime dispatches it, collects the result, and produces a response.

    <Tabs items={["python", "typescript"]}>
      <Tab value="python">
        ```python
        import asyncio

        async def main():
            loop = asyncio.get_running_loop()
            result = await runtime.turn(
                "What's the weather in NYC?",
                context=kaji.TurnContext(
                    principal_id="weather-app",
                    deadline_monotonic=loop.time() + 30,
                ),
            )
            print(result.text, result.session_id, result.turn_id)

        asyncio.run(main())
        ```
      </Tab>
      <Tab value="typescript">
        ```ts
        const result = await runtime.turn("What's the weather in NYC?", {
          context: {
            principalId: "weather-app",
            deadlineAtMs: deadlineAfter(30_000),
          },
        });
        console.log(result.text, result.sessionId, result.turnId);
        ```
      </Tab>
    </Tabs>

    Python's `deadline_monotonic` is absolute monotonic time. TypeScript's
    `deadlineAtMs` is absolute Unix epoch milliseconds; `deadlineAfter()`
    converts a duration for you. Either caller deadline can only tighten the
    runtime's configured whole-turn maximum.

    Tool-capable turns require a per-turn principal unless the host has
    deliberately configured a single-tenant builder default. Handlers receive
    a detached, immutable execution context containing principal, session,
    turn, request, trace, call, idempotency, deadline, and cancellation data.

    To stream events as they happen instead of reading a bounded history page,
    subscribe through the event journal/committer. See
    [event bus](/docs/concepts/event-bus).

  </Step>
</Steps>
