---
title: Troubleshooting
description: Common errors when importing kaji, running a provider, or installing the CLI -- and how to fix each one.
---

If you see one of these errors, try the matching fix below.

## ModuleNotFoundError: No module named 'openai'

You installed `kaji-sdk` without the provider extra.

```bash
pip install "kaji-sdk[openai]==0.2.0b1" # or select another extra at this version
```

In TypeScript, Zod `>=4.3 <5` is required and the provider clients are optional
peers. Install Zod plus the provider you'll use:

```bash
bun add kaji-sdk@0.2.0-beta.3 "zod@>=4.3 <5" openai
```

## ProviderConfigError: `<PROVIDER>_API_KEY` is required

The provider client cannot find its key. For the beta-supported OpenAI path,
export it in your shell or put it in a `.env` file that your runtime loads.

```bash
export OPENAI_API_KEY=sk-...
```

Run `kaji doctor` to verify the key is present. Anthropic, Gemini, Kimi, and
OpenRouter keys are only needed when intentionally evaluating those
experimental/WIP adapters.

## Peer dep version mismatch (TS)

If installation warns about a peer-dependency conflict, check the beta ranges:
`zod >=4.3 <5` and `openai >=4 <8`. Zod is required; OpenAI is optional.
The experimental/WIP Anthropic adapter separately declares
`@anthropic-ai/sdk >=0.30 <2`. Upgrade or pin the conflicting workspace
dependency to the corresponding range.

## `MISSING_TOOL_IDENTITY` or unclassified tool risk

Every enabled tool needs an explicit risk classification. Every turn that can
execute one needs a caller principal. Pass `TurnContext(principal_id=...)` in
Python or `{ context: { principalId: ... } }` in TypeScript. Do not hardcode a
shared principal inside a tool handler. Text-only runtimes may omit identity.

## Tool calls never fire

Three usual causes, in order of likelihood:

1. The tool was registered with `register_tool` / `registerTool` but not
   passed to `AgentBuilder().tool(...)`. The runtime only sees tools
   bound to it.
2. The model wasn't given the spec. Check `kaji info --json` for the
   provider, and confirm your provider's API supports function calling.
3. The model decided not to call the tool. Reduce ambiguity in the
   tool's `description` and parameter docs.

## Events log is empty after a turn

`runtime.history(sessionId)` reads a bounded cursor page from the `EventStore`
you passed (or the default `InMemoryEventStore`). If you instantiated a fresh
store between the turn and the read, it will be empty. Reuse the store and page
with `after_sequence` / `afterSequence`; ordering is by stored sequence, not
timestamp. To stream events as they happen, subscribe through the journal or
committer -- see [event delivery](/docs/concepts/event-bus).

## Provider request failed

Catch the package-root `ProviderError` (`from kaji import ProviderError` or
`import { ProviderError } from "kaji-sdk"`) and inspect
`normalize_provider_error(error)` / `normalizeProviderError(error)`. All Kaji
provider auth, rate-limit, network, configuration, and API failures are
catchable through that type. The normalized fields are safe for routing and
retry policy. Do not log vendor exceptions, response bodies, causes, prompts,
credentials, headers, or tool arguments.

## `import kaji` is slow

The Python SDK uses PEP 562 lazy loading. The top-level import is
cheap; first attribute access triggers a submodule import. If a specific
name is slow on first access, import it directly from its subpackage
(e.g. `from kaji.runtime.tools.registry import ToolSpec`).

## kaji CLI not on PATH after `pip install`

Your shell hasn't picked up the new entrypoint. Restart the shell or
run `hash -r` (bash/zsh). If the CLI is installed inside a virtualenv,
activate the venv (`poetry shell` or `source .venv/bin/activate`)
before running `kaji`.
